# Sharda Social SEO audit and implementation

Audit date: 27 November 2026, Asia/Kolkata. Scope: live `sharda.social`, the
Next.js frontend and Express backend. Implementation is in the repositories;
it has not been deployed. The canonical origin chosen is
`https://www.sharda.social`, matching the site's existing live destination.

## Executive assessment

The largest problem was indexation, not a shortage of keywords. Live responses
for the library homepage, PYQs, notes and syllabus all contained
`noindex, nofollow` for both general robots and Googlebot. Those same URLs
appeared in the sitemap. An inherited directive in `app/library/layout.tsx`
caused the exclusion.

The next priorities were conflicting host signals, mobile loading, search-intent
clarity and useful supporting content. The live apex redirected temporarily to
`www`, while canonical tags, structured data and the sitemap pointed back to
the apex. The old `notes-pyqssharda.vercel.app` hostname also served a 200 copy
of the PYQ page and appeared in search results.

These issues have been addressed in code. The library's existing sign-in
requirements remain in place. Public collection pages and new articles can be
indexed; private document viewers and internal search should not be indexed.

| P2 / Medium | Preview URLs could become metadata origins in the original environment-dependent implementation. | Canonicals always use the production origin. Preview environment logic sets noindex metadata and global noindex response headers. Environment-specific logic was executed and checked; actual preview hosting remains a deployment check. |

The HTTP endpoint already upgraded to HTTPS, `www` pages already used HSTS,
and a sampled unknown public route returned 404. No evidence justified changing
the authentication model or adding language variants. The site uses English
with `en-IN`; no hreflang set is required for a single language site.

## Research and evidence

The guides use primary sources: [official library](https://sharda.ac.in/library),
[library catalogue guidance](https://sharda.ac.in/library/library_glance),
[e-resources directory](https://sharda.ac.in/library/e_sources), university
curriculum PDFs, [NPTEL](https://nptel.ac.in/courses),
[NDLI](https://ndl.iitkgp.ac.in/),
[Zotero documentation](https://www.zotero.org/support/adding_items_to_zotero/)
and [retrieval-practice research](https://pubmed.ncbi.nlm.nih.gov/21707204/).
Each article lists the sources relevant to its task and distinguishes official
facts from editorial study suggestions. No campus hours, universal borrowing
rules, exam predictions, solved-paper claims or fabricated personal experience
were invented. The 2023–27 curricula are labelled as examples for that batch,
not presented as the current syllabus for all students.

Direct source checks are in [source-verification.json](source-verification.json).
The institutional `idp.sharda.ac.in` page could be read through search, but its
direct connection timed out here. The primary access path recommended to
students is the university-maintained e-resources directory, not a potentially
outdated vendor bookmark.

SEO decisions align with Google's guidance on
[consistent canonical signals](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls)
and [concise, descriptive title links](https://developers.google.com/search/docs/appearance/title-link).

## Verification and limits

- Frontend `pnpm build`: passed; 20 article routes are statically generated.
- Backend `pnpm build`: passed.
- Backend `pnpm test`: 7 tests passed.
- ESLint over changed frontend TypeScript/JavaScript files: passed.
- Full frontend `pnpm lint`: reports 31 errors and 39 warnings in pre-existing,
  unrelated code, including explicit-any and effect-state issues. They were
  not suppressed or represented as a clean whole-repository lint result.
- `pnpm seo:verify http://127.0.0.1:4317`: verifies all 27 public pages,
  server-rendered article content, unique metadata, schema, canonical/sitemap
  agreement, public robots rules, filter headers, authentication guards,
  missing pages, image response and both host redirects.
- Preview metadata/header environment logic: passed.

Next.js may stream a 200 shell and a refresh redirect for protected viewers.
Verification checks the actual login destination, noindex header and absence
of an embedded private document, rather than falsely claiming every auth
redirect is an HTTP 307. Unknown public/blog URLs must return an HTTP 404.

Local Lighthouse uses a production frontend build, Edge headless, mobile
emulation and Lighthouse 13.6.0. The local API service was not running, so
API-dependent cards/results were empty or showed their error state. The live
public browse API separately returned 200 for PYQs, notes and syllabus; the
PYQ API reported 11,673 available records at the time of the check. Static
syllabus resources are maintained separately from that API's database results.
Successful authenticated login, document opening and downloads were not tested
with a student account. No account or content data was changed.

Single-run local lab scores cannot establish deployed speed, real-user INP or
ranking improvement. The public PageSpeed API returned HTTP 429, so CrUX/field
data was unavailable. TBT is reported as TBT, not substituted for INP. Mobile
screenshots were inspected for the library and article templates. Other device
sizes, dark mode, account states and real mobile browsers still need deployment
verification.

## Deployment and follow-up, in priority order

1. Deploy frontend and backend changes. Run
   `pnpm seo:verify https://www.sharda.social` from the frontend directory.
   Check the public collections have no noindex header or meta tag and return
   200 with the correct `www` canonical.
2. In Vercel, make apex-to-www a permanent 301/308 domain redirect. The live
   platform currently uses 307, which can run before application redirects.
   Check HTTP, HTTPS, both hostnames, trailing slashes and query preservation
   for a direct path to the preferred URL. Apply the legacy-host redirect in
   its actual project if it is not served by this deployment.
3. Confirm production `BACKEND_ORIGIN`, public collection data, source-file
   availability, sign-in return paths and an actual authorised PDF download.
   Check backend/API noindex headers and preview-deployment noindex headers.
4. Use Search Console URL Inspection on `/library`, `/library/pyqs`,
   `/library/syllabus`, `/blogs` and representative articles. Verify selected
   canonicals and request indexing once. Submit
   `https://www.sharda.social/sitemap.xml`; monitor indexation rather than
   repeatedly resubmitting URLs.
5. Run Google's Rich Results Test and the schema.org validator on deployed
   collection/article samples. Local JSON parsing verifies syntax and identities,
   not eligibility for a Google rich result. Educational FAQ markup does not
   entitle this student site to FAQ rich results.
6. Repeat mobile Lighthouse on deployed library, PYQ, syllabus and blog pages
   with real API content. Check real-device tap targets, filter operation,
   horizontal overflow, loading/error states and PDF behaviour. Review Search
   Console/CrUX LCP, INP and CLS over their field-data window when available.
7. Export Search Console query+page+position data for a dated 28-day baseline,
   keeping device/country/search-type filters consistent. Recheck after roughly
   3–4 weeks and compare equivalent periods. Track library/e-library/syllabus
   CTR, clicks, impressions, position and which URL earns each query; do not
   infer success from a Lighthouse score or from impressions alone.
8. Check for cannibalisation between broad collection owners and supporting
   task guides. Refresh official access links/curriculum references when the
   university changes them. Expand coverage when there is a specific student
   need and a useful resource, not by multiplying near-identical keyword pages.
   The university's [programme curricula directory](https://sharda.ac.in/academics/programme-curricula)
   is an additional starting point when checking other programmes/batches;
   individual entries still need applicability checks.

No increase in impressions, clicks or positions is claimed before deployment,
recrawling and Search Console measurement.
